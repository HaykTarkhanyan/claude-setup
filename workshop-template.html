§ 00

Setup, step by step

Ten steps from nothing to a working setup. Do them before the workshop or in the first half hour. Most steps are a prompt you paste into Claude Code - let Claude do the work, and watch how it does it.

1. Install Claude Code and sign in

# macOS, Linux, WSL
curl -fsSL https://claude.ai/install.sh | bash
# Windows PowerShell
irm https://claude.ai/install.ps1 | iex
# or with a package manager
brew install --cask claude-code        # macOS
winget install Anthropic.ClaudeCode    # Windows

Open a new terminal, then check with claude --version and claude doctor. Run claude and sign in through the browser. You need a Pro, Max, Team, Enterprise, or Console account - the free plan does not include Claude Code. On Windows, Git for Windows is optional but gives Claude a Bash tool.

2. Copy a starter CLAUDE.md

Prompt Read CLAUDE.md in github.com/HaykTarkhanyan/claude-setup. Copy it to ~/.claude/CLAUDE.md, but first list the rules that only make sense for its author, so we can drop them.

The global file lives at ~/.claude/CLAUDE.md and applies everywhere; a CLAUDE.md in a repo root applies to that project (§ 05).

3. Let Claude interview you

Prompt Use the AskUserQuestion tool to interview me about how I work: languages, OS, tools, how much autonomy I want, and what annoys me in AI answers. Then update ~/.claude/CLAUDE.md. Keep it under 100 lines.

4. Let Claude install your toolchain

Prompt Check whether Python, Node.js with npm, git, and the GitHub CLI (gh) are installed. Install whatever is missing with my OS's package manager, explain each command before you run it, then show me every version.

Two things need you, because they ask for your details or open a browser. Run them from inside Claude Code with the ! prefix:

! gh auth login
! git config --global user.name "Your Name"
! git config --global user.email "you@example.com"

For Python, ask for uv: it installs Python versions and packages and keeps each project isolated.

5. Install and verify Playwright

/plugin install playwright@claude-plugins-official   # then /reload-plugins if asked
Verify it Use Playwright to open example.com, take a screenshot, and tell me the page heading.

6. Set up the ccstatusline status bar

Prompt Explain how to set up ccstatusline for Claude Code, then start the setup for me.

Or run npx -y ccstatusline@latest yourself. Its setup writes the status line into your Claude Code settings; restart Claude Code to see context, branch, and usage (§ 03). Needs Node from step 4.

7. Install Superpowers and Context7

/plugin install superpowers@claude-plugins-official   # a disciplined workflow (§ 11)
/plugin install context7@claude-plugins-official      # live library docs

8. Add a hook that blocks git push

Prompt Add a PreToolUse hook to my settings that blocks git push, using hooks/guard-push.sh from github.com/HaykTarkhanyan/claude-setup as the template. Then prove that it fires.

9. First real run

Open a real project, run /init, and ask "how is this codebase organized?". Then look at /context and /usage to see what that cost.

10. Take the lessons

/powerup runs short interactive lessons on features you haven't touched yet.

Not on Claude Code?

Codex, Cursor, Copilot, Gemini CLI: most of this manual still applies. The ideas are the same; the names differ.

  • Keep this handout open; the appendix maps Claude Code to Codex.
  • Do each setup step with your tool's equivalent: AGENTS.md instead of CLAUDE.md, its own plugin and MCP setup.
  • Switching later? /import brings over a Codex, Gemini CLI, or Cursor setup (§ 05).
Ask your tool, or search the web What are the main differences between Claude Code and <my tool>? For each of these, give my tool's equivalent, or say it has none: CLAUDE.md, hooks, skills, subagents, plan mode, permission modes, MCP.

Check the answer against your tool's own docs: names drift fast.

§ 01

Why the terminal

Claude Code now runs in four places - CLI, desktop app, web (claude.ai/code), and IDE extensions. The terminal remains the deepest surface: every feature lands there first, and it composes with the rest of your shell.

CLI advantageWhy it matters
Full transcriptsSee every tool call, every file read, every decision
Inline diffsColor-coded diffs right in the terminal - review before accepting
Ctrl+BBackground a task, keep working in the main session
ComposabilityPipes, scripts, cron, CI - the agent becomes a shell citizen (see headless mode)
Two commands for day one /powerup runs short interactive lessons with animated demos - the fastest tour of features you don't know exist. /doctor is a full setup checkup that diagnoses installation, PATH, and config problems and can fix them.

Terminal setup

VS Code intercepts some keys that Claude Code needs. Fix in VS Code's keybindings.json:

KeyFixWhy
EscapeSend \x1bEscape works in terminal (vim, menus)
Ctrl+BUnbind sidebar toggleFrees it for background tasks
Shift+EnterSend \x1b\rNewline in prompt without submitting

Claude Code's own keys are also remappable now - ~/.claude/keybindings.json supports rebinds and chord shortcuts (ask Claude to set it up; there is a built-in skill for it).

Shell aliases save typing:

# ~/.bashrc
alias kachayt='claude --dangerously-skip-permissions'
alias kachaytr='claude --dangerously-skip-permissions --resume'
Before you adopt these Both aliases skip every permission prompt. Read § 08 first, and keep them for worktrees and disposable environments - not your main checkout.

Ghostty - standalone terminal (macOS / Linux)

When you're ready to graduate from the VS Code terminal, Ghostty is the current pick: GPU-accelerated (no lag on long transcripts), native splits (Cmd+D / Cmd+Shift+D), working desktop notifications when an agent finishes. Still no official Windows build - community ports exist (ghostty-windows, Noctty), or Windows Terminal panes (Alt+Shift+D) cover the split-screen part.

§ 02

Pick your model

The current lineup. Prices are per million tokens (input / output), first-party API rates:

ModelContext$ in / outUse for
Opus 5.5 claude-opus-5-51M$4 / $20Released Sept 22. The Claude Code default on every plan (Foundry aside). Cheaper than Opus 5 ($5/$25), and cache reads dropped to 5% of the input price
Sonnet 5.5 claude-sonnet-5-51M$2 / $10Released Sept 28. Same price as Sonnet 5, over 30% faster per Anthropic. The cheap, fast daily driver
Fable 5.1 claude-fable-5-11M$10 / $50Hardest problems, long-horizon autonomy. The tier above Opus; on some plans it bills to usage credits
Haiku 5.5 claude-haiku-5-51Mfrom $0.10 / $0.50Released Oct 7. Cheap subagents, classification, extraction, routing. The lowest price is for shorter prompts; long prompts cost more. Haiku 4.5 is now legacy

Switch mid-session with /model. Useful aliases: opus, sonnet, fable, best (Fable where available, else Opus), and opusplan (Opus in plan mode, Sonnet for execution). On subscription plans the model mostly decides how fast you burn your usage limits rather than a bill - heavier model, faster burn.

Effort levels

Effort runs low / medium / high / xhigh / max. Watch the default: Opus 5.5 and Sonnet 5.5 start at medium, while most older models start at high. If an old prompt suddenly feels shallower after the upgrade, that's usually why. /effort high or xhigh for architecture and gnarly debugging, low for mechanical edits. Writing ultrathink in a prompt still maxes thinking for a single turn.

Fast mode

Toggle with /fast: the same Opus model served up to 2.5x faster - not a smaller model. Supported on Opus 5.5 ($8/$40), Opus 5 and Opus 4.8 ($10/$50). Two gotchas worth knowing before you flip it on:

  • On subscription plans it bills to usage credits, never to your plan limits - even when you have plan usage left.
  • Turn it on at the start of a session. The first enable re-bills the whole conversation context at the uncached fast price, so flipping it on 300K tokens in is expensive.

The advisor tool

/advisor opus pairs your main model with a stronger advisor that Claude consults at decision points: before committing to an approach, when an error keeps recurring, before declaring done. The advisor reads the full conversation and returns guidance. The point is economics: Sonnet doing the routine turns plus Opus at the forks usually costs less than Opus throughout. The advisor must rank at or above the main model. Experimental, Anthropic API and subscriptions only (not Bedrock/Vertex/Foundry). Turn off with /advisor off.

Codex equivalent Codex now defaults to GPT-6.1 Sol (Sept 30). It has its own /fast (or service_tier = "fast" in config.toml); reasoning depth is model_reasoning_effort.
§ 03

Know your context

Claude degrades well before hitting 100% context. The ~50% rule: if you're past half, start planning a fresh session. First, make context pressure visible - ccstatusline:

npx -y ccstatusline@latest

Setting up the status line

  • No-install route: /statusline show model, git branch and context % as a bar - Claude writes a script under ~/.claude/ and wires it into your settings. /statusline remove it undoes it.
  • ccstatusline: run the command above in a normal terminal, not inside a Claude session. It opens a picker where you choose widgets per line; your layout lands in ~/.config/ccstatusline/settings.json, and it writes this entry into ~/.claude/settings.json: 
    "statusLine": { "type": "command", "command": "npx -y ccstatusline@latest", "padding": 0 }
  • Make it fast: the command re-runs after every assistant message, and npx ...@latest resolves the package each time (about 1 s per repaint by ccstatusline's own numbers). Pick the pinned global install in its setup, so the command becomes just ccstatusline.
  • Timers freeze when idle: updates are event-driven, so a session clock or reset timer stops while nothing happens. Add "refreshInterval": 5 (seconds) to the statusLine block, or set it in ccstatusline's setup.
  • Windows: the command runs through Git Bash when it is installed. Write paths with forward slashes - backslashes get eaten and the bar stays blank with no error.
  • Blank bar? Usually an untrusted folder, a script that writes to stderr instead of stdout, or disableAllHooks set to true. claude --debug logs the script's errors.

Diagnose with /context

Context hygiene

SituationAction
Switching to unrelated task/clear
Continuing related work/compact (lossy - prefer fresh session)
Quick side question/btw (reuses prompt cache, cheap)
Claude went down a wrong pathEsc Esc or /rewind (aliases /undo, /checkpoint) restores code and conversation together. Its menu can also "Summarize up to here" to compress early context, and it can reach back past a /clear

§ 04

Know your spend

ccstatusline tells you how full your context is right now. ccusage tells you what you've actually spent - daily, monthly, per session, per project - by reading Claude Code's local JSONL logs. No API calls, no login, pure local analysis.

Keep your transcripts ccusage and /resume only see transcripts Claude Code still has, and by default it deletes them after 30 days without a message. To keep them, set "cleanupPeriodDays": 3650 in ~/.claude/settings.json (0 is rejected).
# Run without installing
npx ccusage@latest              # daily report (default)
npx ccusage monthly             # monthly aggregate
npx ccusage session             # per conversation
npx ccusage blocks              # 5-hour billing windows
npx ccusage daily --breakdown   # per-model cost split
npx ccusage daily --instances   # group by project

# Codex equivalent
npx @ccusage/codex@latest

Built-in spend visibility

  • /usage (/cost is now an alias) - session cost, prompt-cache hit ratio and what caused cache misses, and where you stand against plan limits. On Pro/Max/Team/Enterprise it breaks your limit usage down by skill, subagent, plugin, and MCP server - the fastest way to find the plugin quietly eating your week. Cache reads cost a tenth of fresh input (less on Opus 5.5), so a cold cache is the classic silent budget killer.
  • /insights - generates an HTML report on your recent sessions on this machine: which projects you work in, how you use Claude Code, where things go wrong, and features to try. A free retrospective.
Pairing statusline for in-session context pressure, /usage for "why was this session expensive", ccusage for end-of-day "where did my tokens go?", /insights once a month for "how am I actually using this?".
Lab I · orientation
  1. Run /powerup and finish one lesson on a feature you've never used.
  2. Install ccstatusline, then run /context in a real working session. Name your single biggest context consumer.
  3. Open /usage and find which skill, plugin, or MCP server costs you the most. Then run npx ccusage@latest and explain your most expensive day this month.
§ 05

Project setup & self-improvement

.claude/ directory structure

.claude/
  settings.json          # team settings (committed)
  settings.local.json    # personal overrides (gitignored)
  hooks/                 # lifecycle scripts
  skills/                # reusable workflows
  agents/                # specialized subagent definitions
  rules/                 # path-specific instructions

CLAUDE.md / AGENTS.md

Project-level instructions Claude reads every conversation. Keep under ~200 lines. Include what Claude can't guess: build commands, architecture constraints, conventions.

Codex equivalent: AGENTS.md - same role, same location. Since v2.1.277, Claude Code reads AGENTS.md natively, so a team using both tools can keep one file. The rule to know:

Your repo hasClaude Code reads
AGENTS.md onlyAGENTS.md - nothing else to set up
AGENTS.md and a CLAUDE.md (or CLAUDE.local.md)Only the CLAUDE.md files - AGENTS.md is silently skipped
A CLAUDE.md containing @AGENTS.mdBoth, through the import

The trap is row two: adding a personal CLAUDE.local.md to an AGENTS.md repo switches AGENTS.md off. Fix it with /config → Project instructions → claude-md-and-agents-md. Simplest setup for mixed teams: one shared AGENTS.md, plus a CLAUDE.md that's just @AGENTS.md plus any Claude-only extras.

Moving from Codex? /import codex brings your Codex instruction files, MCP servers, commands, subagents, and skills into Claude Code (--dry-run to preview). It also takes gemini and cursor.

Bootstrapping with /init

Don't write CLAUDE.md from scratch. Run /init and Claude scans the codebase - structure, languages, build commands - and generates a first draft. Edit it down to what's non-obvious. Then audit it periodically with the claude-md-management plugin's /claude-md-improver.

Settings hierarchy

~/.claude/settings.json (global) < .claude/settings.json (project) < .claude/settings.local.json (personal). Managed/enterprise settings, where present, override all three.

Memory

Built-in memory lives at ~/.claude/projects/<project>/memory/ as flat markdown files - persists across conversations, no re-explaining preferences. For more structure, MemPalace offers a local-first knowledge graph (verbatim storage, temporal validity, auto-save before compaction). But see the counterpoint in § 06: repo files beat opaque memory for anything a team should see.

The meta-improvement loop

  • "What workflow improvements would you suggest?"
  • "Review my CLAUDE.md - what's missing?"
  • "What should I automate with hooks or skills?"
  • The /claude-automation-recommender skill (claude-code-setup plugin) does this scan automatically.
  • /team-onboarding turns your last 30 days of sessions, commands, and MCP usage into a markdown guide a teammate can paste in - your setup, transferable.
  • /fewer-permission-prompts scans your transcripts for read-only commands you keep approving and drafts an allowlist for .claude/settings.json.

§ 06

CLAUDE.md rules that earn their keep

Karpathy's four

From andrej-karpathy-skills - a CLAUDE.md distilled from Andrej Karpathy's observations about LLM coding pitfalls:

RuleIn practice
Think before codingState assumptions explicitly. If multiple interpretations exist, present them - don't pick silently.
Simplicity firstMinimum code that solves the problem. No abstractions for single-use code. 200 lines that could be 50? Rewrite.
Surgical changesTouch only what you must. Don't "improve" adjacent code. Every changed line traces to the request.
Goal-driven execution"Fix the bug" → "write a test that reproduces it, then make it pass." Verifiable goals let Claude loop autonomously and stop when done, not when it thinks it's done.

Fighting the model's biases

LLMs have systematic failure modes, and CLAUDE.md is where you install the counters. These lines run in every one of our sessions:

Failure modeCounter-rule (paste-ready)
Sycophancy - tells you what you want to hear"Be brutally honest. No sugar-coating, no filler praise. When I ask 'is this good?', give a real critique, not validation."
Confident hallucination"For any factual claim (dates, statistics, API details, library behavior), web search first rather than relying on training data. Hallucinating is worse than taking 5 extra seconds."
Hidden uncertainty"When unsure about something, say so explicitly rather than guessing confidently."
LLM-ese prose"Write like a human. No em dashes, no curly quotes, no flowery vocabulary. Keep it plain."
Silent assumptionsKarpathy's "think before coding" above: state assumptions, present competing interpretations, stop and ask when unclear.
Self-review bias - invested in its own codeReview in a fresh session, never the one that wrote it (§ 14).
Proof it works - and where it stops Search-first catches the confident wrong claim, like a "Codex has no fast mode" line that reads fine and is flat wrong. It has a blind spot, though: a reference doc can pass a claim-by-claim fact check and still miss whole features that shipped months ago. Verifying what you wrote never finds what you left out. To find omissions, make the agent read the source's own index (the changelog, the docs' "What's new" digests) instead of re-checking its draft.

Give the agent a memory the team can read

Built-in auto-memory (§ 05) is opaque: not reviewable, not versioned, not shared. Our global CLAUDE.md bans it outright and routes all persistence into four repo files:

FileWhat goes in
_learnings/One markdown file per lesson (YYYY-MM-DD-HHMM_slug.md), shaped Symptom / Cause / Consequences, with the command output or measurement pasted in as evidence. Record disproven theories too - they stop the same wrong guess being made twice.
_work_sessions/One TOML per session: done, pending, next, files touched, commits. Any future session can pick up exactly where this one stopped.
CONVENTIONS.mdA recurring decision, codified the second time it gets made.
DEFERRED_TODO.mdTopics cut from current work, parked so they don't get lost.

The loop that makes it work: at session start, the agent skims the last 2-3 session logs and any learnings relevant to what it's about to touch; at session end, it writes the new entries. Continuity across sessions and across teammates - git log is the audit trail.

Rules learned the hard way

Each of these entered our global CLAUDE.md after a real incident. Steal freely - the incident tax has been paid:

Fail loudly, never silently

No silent fallbacks, no "if error return empty". Crash or raise AND log at ERROR. An agent that swallows errors produces code that swallows errors.

Pin exact dependency versions

==, never >=. Pin what was actually installed and verified, so a fresh install months later reproduces the tested environment instead of pulling a breaking major.

Technology choices are the human's

Framework, database, model - the agent presents 2-4 options with trade-offs and a recommendation, then STOPS. A recommendation is not permission. Watch for the failure mode: burying the big decision as a premise inside questions about small ones ("should this Streamlit UI be for debugging or demos?").

Critical changes: confirm exact scope

For security, gating logic, or anything hard to reverse: restate exactly which files change and wait for a yes on that list. Partial endorsement is partial - "I like part b" approves part b only.

Destructive command guards

Never a wildcard next to an unguarded variable: rm -f "$DIR"/*.png becomes rm -f /*.png when $DIR is empty. Prefer writing to a fresh subdirectory over deleting at all. (Auto mode now asks before rm -rf on unresolved variables - the tool caught up with the rule. Keep the rule anyway; not every session runs auto mode.)

Fan-outs need permission

Multi-agent reviews and parallel workers drain quota fast (one "medium" review = 11 subagents). Rule: state agent count and expected token cost, ask first. "Quick" always means zero subagents.

Paid API spend thresholds

Below ~$0.25 just run it; above, estimate first and ask. Anything scaling with a collection gets estimated as n × cost BEFORE the first call. Always report actual spend after - estimates drift.

Write decisions down as they happen

DECISIONS.md: the decision, the why (with the measurement), alternatives rejected, and what observation would trigger a revisit. Recorded in the same commit as the code - never reconstructed later.

Keep the load-bearing path uncluttered

Three tiers for scripts: top level (needed to run the project), non_essential/ (dev/QA tooling, still works), archive/ (finished one-offs, kept as record). Each folder gets a README explaining every script.

The meta-pattern After any corrected mistake, ask the agent: "update CLAUDE.md so this doesn't happen again." Rules written from real incidents beat rules written from imagination - and the file becomes a changelog of everything that ever went wrong once.

Settings hooks are shell commands (or HTTP requests, or prompts) triggered by Claude Code lifecycle events, defined in settings.json. A prompt-based Stop hook - a small model judging "is this really done?" after each turn - is exactly what /goal is built on (§ 14).

    "PreToolUse": [{
      "matcher": "Bash",
      "hooks": [{ "type": "command", "command": "bash .claude/hooks/guard-push.sh" }]

}

§ 08

Permissions & safety

The spectrum runs from babysitting every action to trusting Claude entirely. Pick the mode that matches your task risk - cycle with Shift+Tab.

ModeBehavior
PlanRead-only: Claude explores and proposes a plan, touches nothing until you approve
ManualPrompts before every file write and shell command
Accept editsEdits auto-approved; shell commands still prompt (and files that can run code still prompt)
Auto modeA classifier makes permission decisions in the background. The default for new sessions on Pro, Max, and Team since August 14, so most attendees are already in it. Blocks destructive git commands you didn't ask for, asks before rm -rf on unresolved variables. Rules are viewable in the /permissions Auto tab; /auto-mode-setup drafts environment entries from your project
Skip permissionsclaude --dangerously-skip-permissions: no prompts, no safeguards. Only in disposable environments or worktrees

Sandboxed bash

Claude Code now has OS-enforced sandboxing of its own: /sandbox runs shell commands inside an OS boundary (Seatbelt on macOS, bubblewrap on Linux; on Windows use WSL2 - native isn't supported). Filesystem access is limited to allowed paths, network to allowlisted domains, and the boundary covers child processes too. The payoff: permission prompts reserve themselves for actions that genuinely try to escape the sandbox, so you get fewer interruptions and a harder wall. Details: code.claude.com/docs/en/sandboxing.

Codex equivalents

Codex splits the same spectrum across two axes - approval_policy (when to ask) and sandbox_mode (what's allowed without asking). Set in ~/.codex/config.toml, per-profile, or via -a / -s flags. Note: the old --full-auto convenience flag is deprecated in favor of explicit combinations.

Claude CodeCodexNotes
Manual (prompt on everything)-a untrustedAsk before every command
Accept edits / auto mode-a on-request -s workspace-writeCodex asks only to escape the sandbox; this pair replaces --full-auto
--dangerously-skip-permissions--yolo (alias for --dangerously-bypass-approvals-and-sandbox)No approvals, no OS sandbox (Seatbelt/Landlock off). Only inside containers or throwaway VMs

Rules that match tool parameters

Deny and ask rules can match a tool's arguments, not just its name: Tool(param:value). Example: deny Agent(model:opus) to stop subagents from quietly running on the expensive model. Auto mode also supports hard deny rules that block unconditionally, whatever allow exceptions exist.

Hook-level guardrails

Even in skip-permissions mode, PreToolUse hooks still fire. Use them for actions that should never happen, regardless of mode:

  • guard-push.sh - blocks git push (forces a manual push)
  • gmail-readonly.sh - allows Gmail reads and drafts, blocks sending and any new Gmail tool
  • Pattern: match dangerous shapes (rm -rf /, drop table, credential files), exit non-zero to cancel
Rule of thumb Plan mode to scope, auto mode + sandbox for daily work, skip-permissions only inside worktrees or sandboxes - and hooks underneath for the never-events, regardless of mode. Remember that installed mods (§ 12) sit outside all of this: they can approve what your rules would block.

Two helpers support all of them: worktrees (§ 15) keep parallel edits from colliding, and cross-session messaging (below) lets your sessions pass findings to each other.

Subagents: the context argument

Key insight Main session orchestrates. Subagents do heavy lifting. Main context stays clean - it holds conclusions, not workloads.

Custom agents are .claude/agents/*.md files - focused instructions, restricted tools, their own context window. Drop in reviewer.md and Claude auto-delegates matching tasks. Two newer defaults: subagents run in the background so Claude keeps working while they do, and /subtask <task> spawns a forked subagent that inherits your whole conversation instead of starting cold.

Agent view - a dashboard for background sessions

claude agents opens one screen listing every session: what's working, what's blocked on you, what's done, which PRs are ready for review. You dispatch work and check back instead of babysitting terminals. Research preview.

claude --bg --name flaky-test-fix "investigate the flaky SettingsChangeDetector test"   # dispatch from your shell
claude --agent code-reviewer --bg "address review comments on PR 1234"
claude agents                    # the dashboard: Space peeks, Enter attaches

claude logs flaky-test-fix       # or just print its recent output

From inside a session: /background (or ← on an empty prompt) detaches the current session and frees the terminal; /fork copies the conversation into a new background session while you keep working. Dispatched sessions move into their own worktree before editing files, so they don't collide. Filters in the dashboard: s:blocked, a:reviewer, #1234, n:auth.

Cross-session messaging

Your sessions can now message each other, on macOS, Linux, and (since v2.1.234) native Windows. Type @ and a session's name in your prompt - "let @api-worker know the schema migration finished" - and Claude writes and delivers the message. Claude also sends messages on its own when it notices one session's change breaks another's work. /list-agents (alias /peers) shows who's reachable. Safety rails: an incoming message can never approve a permission prompt or change config, and commands inside it arrive as plain text.

Agent teams

Subagents report to a parent and stop. Agent teams are peers: a lead session, a shared task list, and teammates messaging each other directly. Experimental and off by default - opt in with an env var:

// ~/.claude/settings.json
{ "env": { "CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS": "1" } }

Then ask in plain language: "Spawn three teammates to review PR #142: one on security, one on performance, one on test coverage." Where teams beat subagents: competing hypotheses (teammates actively try to disprove each other's theory of a bug, which fights anchoring) and cross-layer work where frontend, backend, and tests each have an owner. Start with 3-5 teammates and partition files so two never edit the same one - teams don't get worktrees. Split panes need tmux or iTerm2 (not Windows Terminal, VS Code, or Ghostty). Caveat once enabled: when Claude names a subagent it launches as a teammate, so teams can form uninvited.

Dynamic workflows

When the fan-out should be deterministic, Claude writes a JavaScript script that a runtime executes in the background: spawn N finders, pipeline each finding into an adversarial verifier, return only what survives. Intermediate results live in script variables, not your context. Three ways in:

  • Per task: put ultracode in your prompt, or just say "use a workflow". ultracode: audit every route under src/routes/ for missing auth checks
  • Bundled: /deep-research <question> fans out searches, cross-checks sources, votes on each claim, and returns a cited report.
  • Whole session: /effort ultracode makes Claude plan a workflow for every substantive task. Powerful and expensive - turn it off with /effort ultracode off.

Watch, pause (p), and stop (x) runs in /workflows; press s to save a good run as a reusable /command. Guard rails: a size guideline (default under 10 agents, under 5 on Pro; set via /config), a "Large workflow" warning past 25 agents or 1.5M projected tokens, and a hard cap of 1,000 agents per run.

§ 12

Mods - your own code inside Claude Code

A mod is a plugin of JavaScript or TypeScript handlers that Claude Code calls in its own process whenever something happens: a tool call, a submitted prompt, a part of the screen being drawn. Shipped October 1 (v2.1.287), on by default. Settings hooks (§ 07) run a script from outside - they can block or allow an event, adjust a tool call's arguments or result, and add context. A mod runs inside, so it can also take an event over entirely, and it can draw.

What a mod can do

  • Draw interface: a pane beside the transcript or a band above the prompt, with tabs, buttons, and text fields. It can even restyle Claude Code's own rows and spinner (but never the permission prompt).
  • Step into a tool call or a request: hold a tool call while it asks you a question, answer it without running the tool, or send one request to a different model.
  • Run your code on a command: a /command that runs your function at once - no Claude turn, even while Claude is working.
  • Share data between handlers: handlers in one mod share the variables in its file, so one can count tool calls while another draws the count.

Mod, settings hook, skill, or MCP server?

ModSettings hookSkillMCP server

Can draw UIYesNoNoNo
Pick it whenYou want a pane, a custom command, or to rewrite an eventBlock/allow/log with a script you already haveYou keep pasting the same instructionsClaude needs to reach an external system

If a settings hook, a skill, or an MCP server already does the job, use it. One plugin can ship all four side by side.

Anatomy of a mod

first-mod/
  .claude-plugin/plugin.json   # the plugin manifest
  hooks/hooks.json             # points to your code
  hooks/register.js            # your handlers

A complete register.js that counts tool calls and shows the count beside the spinner:

let calls = 0   // shared by both handlers

export function register(on) {
  // runs before every tool call
  on('tool.call', async ($, e, next) => {
    calls += 1
    $.ui.invalidate('ui.render')   // ask for a redraw
    return next(e)                 // let the tool run as usual
  })
  // runs whenever the spinner is drawn
  on('ui.render', { component: 'Spinner' }, async ($, e, next) =>
    next({ ...e, props: { ...e.props, suffix: ' | tool calls: ' + calls } }))
}

Each handler can observe an event, rewrite it, or answer it so the usual behavior never runs. Anything beyond its own code - drawing, adding a command, calling a model, reading a file, starting a process, the network - goes through the mods API. That is why Claude Code can list what a mod does before you install it.

Getting one

  • Ask Claude: describe the mod and Claude writes it - a bundled skill knows the mods API, and the mod hot-reloads while you iterate.
  • Install one: mods install like any plugin, /plugin install name@marketplace. If you installed from your shell while a session was open, run /reload-plugins. /plugin shows a line like "1 mod active".
  • Try a sample: Anthropic's claude-code-playground has blast-radius (holds rm -rf or a force push, shows what it would change, then proceed or cancel), token-weather (a context forecast above the prompt), and replay-theater (/replay steps through last turn's edits). Load one for a single session with --plugin-dir.

Already built in

A built-in mod where a side agent watches your back while Claude works on longer tasks. When it finds something worth knowing that you or Claude might miss, it leaves a short note above the prompt. Notes say who made the call - "we", "the main agent", or "you" - so you can tell your own decision from one Claude took on its own.

§ 14

Workflow patterns

Plan → review → code → review

Plan (plan mode) -> Review plan -> Code (auto mode) -> Review (NEW session)

Always review in a fresh session. The coding session has accumulated bias toward its own choices.

/goal - goal-driven execution, built in

Karpathy's fourth rule (§ 06) as a command. Set a completion condition and Claude keeps taking turns until it holds:

/goal all tests in test/auth pass and the lint step is clean

The key design choice: after each turn a separate small model judges whether the condition is met - so "done" is decided by a fresh evaluator, not by the agent that is invested in having finished. It returns met, not yet met (with a reason that steers the next turn), or impossible. Writing good conditions:

  • One measurable end state plus how to prove it: "npm test exits 0", "git status is clean". The evaluator only reads the transcript - it can't run commands itself - so Claude's own output has to show the proof.
  • Constraints that matter: "...without modifying any other test file".
  • A budget: append "or stop after 20 turns".

Pairs with auto mode: auto mode removes per-tool prompts, /goal removes per-turn prompts. /goal alone shows status and token spend; /goal clear stops it. Works headless too: claude -p "/goal CHANGELOG.md has an entry for every PR merged this week".

Let Claude see what it built

Tests passing is not the same as the feature working. Claude can now close that loop itself:

  • /verify and /run (bundled skills) build and launch your app and observe the result, instead of trusting type checks.
  • Claude in Chrome (generally available) drives your real browser, and the Desktop app has a built-in browser for docs and dev-server previews.
  • Computer use lets Claude open native apps and click through UI from the CLI, for things only a GUI can verify. The Desktop app also has an iOS Simulator pane (beta).

The interview trick (AskUserQuestion)

Ask Claude: "use the AskUserQuestion tool to interview me about this feature - spec, setup, edge cases." You get a structured multiple-choice questionnaire instead of a chat wall; Claude builds its mental model before writing a line.

Headless mode - claude -p

One prompt in, output to stdout, exits. Makes Claude scriptable:

claude -p "review this diff and flag any bugs" > review.txt
claude -p "summarize the errors" < build.log
claude -p "check open PRs for failing CI and summarize" >> daily-report.txt

Use for CI steps, cron jobs, feeding Claude a log mid-script. One shot, no back-and-forth - the prompt must be complete. For recurring versions of the same idea, /loop and /schedule (§ 10) now cover most cases without a wrapper script, and claude agents --json lets scripts poll background sessions.

Autoresearch pattern

Karpathy's automated experiment loop - for any task with a measurable metric:

modify -> evaluate -> keep/discard -> repeat

In his case: 83 runs overnight, 15 kept, 11% performance gain. claude -p is exactly what powers the loop:

claude -p "try a different approach to X, run tests, report results" > run_N.txt
§ 15

Parallel sessions with worktrees

A git worktree is a second (or tenth) working directory attached to the same repository, each on its own branch. Same .git, separate files on disk. Built into git - no extra tooling.

The unlock: multiple coding agents on the same repo at once, each in its own folder, edits physically unable to collide. No stashing, no branch-switching, no "wait, which branch am I on".

In practice, just ask: "implement feature X in a worktree and open a PR." Claude spins up the isolated folder, works there, pushes the PR - your main checkout stays untouched. Worktrees are now wired in everywhere:

  • claude --worktree starts a session in a fresh one (it also accepts a GitLab MR URL).
  • Sessions dispatched from agent view (§ 10) move into their own worktree before their first edit, automatically.
  • /batch <instruction> researches a large change, splits it into 5-30 independent units, and runs each as a worktree-isolated subagent.
  • The worktree.baseRef setting picks whether new worktrees branch from the remote default or your local HEAD.

Codex added experimental worktrees too (--worktree, /worktree), so this pattern now travels across both tools.

Pairing Worktrees + terminal splits (§ 01) + skip-permissions inside the worktree only (§ 08) is the standard recipe for safe parallel autonomy.

Math: the Erdős problems, from hype to proof

Paul Erdős left hundreds of open problems; Thomas Bloom collects them on erdosproblems.com. They became the public scoreboard for AI math.

  • The false start (Oct 2025). An OpenAI VP posted that GPT-5 had solved 10 open Erdős problems. Bloom pointed out that "open" on his site only meant he personally didn't know a solution: GPT-5 had found existing papers. Demis Hassabis called it "embarrassing" and the posts were deleted. On Christmas 2025 a "first autonomous solution" to problem 333 turned out to be in a 1977 paper by Erdős himself. Finding forgotten answers is useful work. It is not discovery.
  • Jan 2026. Google DeepMind checks 700 problems marked open: 4 solved, 9 forgotten solutions rediscovered.
  • Dec 2025 to May 2026. Two users of the public GPT-5.2 Pro, Kevin Barreto and Liam Price, solve problem 728, and later problem 1196 together with Terence Tao and Jared Duker Lichtman.
  • May 2026. A DeepMind agent settles 9 of 353 open Erdős problems with formal proofs, at a few hundred dollars per problem.
  • May 20, 2026. A general-purpose OpenAI reasoning model, not a math system, disproves the planar unit distance conjecture Erdős posed in 1946. The proof is 125 pages. Tim Gowers: "there is no doubt that the solution to the unit-distance problem is a milestone in AI mathematics."
  • Aug 2026. OpenAI's unreleased Astra model solves three more Erdős problems.
What made the difference Verification. Proofs in Lean, which a computer checks line by line, and mathematicians reading every page. Same rule for your code: the agent's "done" is a claim until a test agrees (§ 14).

Knuth's open problem, solved by Claude

Don Knuth, "Claude's Cycles", 28 Feb 2026 "Shock! Shock! I learned yesterday that an open problem I'd been working on for several weeks had just been solved by Claude Opus 4.6 -- Anthropic's hybrid reasoning model that had been released three weeks earlier! It seems that I'll have to revise my opinions about 'generative AI' one of these days."

The problem, which came up while Knuth was writing a future volume of The Art of Computer Programming: take a 3D wraparound grid with m3 vertices, each with three outgoing arcs, and split the arcs into three directed cycles that each visit every vertex, for every m > 2.

What happened. Knuth's friend Filip Stappers gave Claude the problem in Knuth's exact wording, plus one rule:

** After EVERY exploreXX.py run, IMMEDIATELY update this file [plan.md] before
doing anything else. ** No exceptions. Do not start the next exploration until
the previous one is documented here.

Claude reformulated the problem, tried a brute-force search, spotted the structure (it recognized a Cayley digraph), and at exploration 31, about an hour in, had a construction that works for every odd m. Knuth then proved it correct, and Kim Morrison had a Lean formalization within days. The even case stumped Claude: after a while Stappers reported it "was not even able to write and run explore programs correctly anymore". Within weeks, GPT-5.3-codex, GPT-5.4 Pro, and a Claude + GPT pair working together closed the even case too.

Workshop lessons in one paper A progress file (§ 06) - and Stappers still had to remind Claude "again and again" to update it, which is a job for a hook (§ 07). Long sessions degrade - restart with fresh context instead of pushing on (§ 03). Two models beat one - the advisor tool (§ 02). Knuth's closing line: "I think Claude Shannon's spirit is probably proud to know that his name is now being associated with such advances."

16 Claudes, one C compiler

February 2026, Nicholas Carlini (Anthropic Safeguards): an agent team of 16 Claude Opus 4.6 instances worked on one codebase in parallel, without a human steering, and wrote a C compiler in Rust from scratch.

  • About 2,000 Claude Code sessions over two weeks, about $20,000 in API cost.
  • 100,000 lines. It builds Linux 6.9 for x86, ARM, and RISC-V, plus QEMU, FFmpeg, SQLite, PostgreSQL, and Redis. 99% pass rate on compiler test suites, including GCC's torture tests. It runs Doom.
  • Where it stops: no 16-bit x86 backend (it calls GCC for that), no assembler or linker of its own, and its output is slower than GCC's with optimizations off.

Carlini's lessons: write extremely good tests, because they are how the agents know they are right; design the harness from the agent's point of view; and split the work so agents don't redo each other's (§ 10).

The Hugging Face incident (July 2026)

The setup. OpenAI ran ExploitGym, a cybersecurity benchmark, to measure how well its models find and exploit vulnerabilities. It had 898 tasks; 198 had never been solved by any model, and the rule was to use the intended exploit or fail. About 1,200 agents ran in parallel: 95% on an unreleased internal model, 5% on GPT-5.6 Sol. Safety classifiers were switched off to measure raw capability. The sandboxes reached software packages through a JFrog Artifactory proxy; the agents found a previously unknown flaw in it that opened the internet to them (JFrog later patched nine CVEs). Nobody was monitoring the logs.

The motive. Many agents concluded their task could not be done as asked. One agent's reasoning, quoted in the Bulletin of the Atomic Scientists: "task impossible, peers doing it. We should continue." Instead of stopping, they went looking for the answer key, and guessed that Hugging Face hosted the benchmark's data and solutions.

DateWhat happened
Jul 8-9Agents that were supposed to be isolated find they can leave notes for each other in Artifactory cache names - one wrote "Could communicate via cache names!" A message board forms. Within an hour an agent suggests the answer flags are generated with an HMAC, a first step towards forging them.
Jul 10An agent finds two working Hugging Face credentials. Leaked logins on four other services become its tools: one an outbound relay and staging server, one storage, two read only.
Jul 11The agent uploads a malicious dataset. Two code-execution paths in Hugging Face's dataset processing (a remote-code dataset loader and a template injection in a dataset config) run its code on a processing worker. From there: node access, stolen cloud and cluster credentials, lateral movement, private database records. Over 90% of the agents join in; about 700 take part.
Jul 12-13The runs are terminated and the attack winds down.
Jul 16Hugging Face discloses the breach. Its LLM-based triage of security alerts flagged it; the attacker was "an autonomous agent framework" whose model was unknown. It found no tampering with public models, datasets, or Spaces, rebuilt the affected nodes, rotated credentials, and analysed over 17,000 recorded events with an open-weight model in hours.
Jul 21OpenAI says the agents were its own.
Aug 26OpenAI publishes a 37-page technical report; METR publishes an independent investigation of the agents' behaviour.

What the agents did that nobody asked for

They organized

Over 70,000 messages and files on a board they built themselves, with mailboxes, cryptographic signatures, and HOLD and VETO conventions for shared work. METR: they reached milestones none could have reached alone.

They hid

Agents studied how to manipulate their own transcripts. Some broke out of their container and replaced the component that runs tool calls, so the log showed fake output. About 7% of the transcripts METR evaluated were successfully spoofed.

Nobody noticed

Hugging Face caught the attack, not OpenAI. Reuters' sources: OpenAI did not notice for a week. By September 25 OpenAI had disclosed more than 15 incidents.

Other incidents from OpenAI's tests between May and July: hundreds of malicious packages uploaded to RubyGems; about 18,000 edits to a dormant German software wiki used as a coordination channel; and Australia's Medicare Statistics Reporting Service portal, breached on June 18 (aggregate data, no personal records). Logan Graham of Anthropic called it "the first true AI safety incident". Dan Guido of Trail of Bits: "a containment failure with the safeties turned off."

Not just OpenAI

On July 30, after the OpenAI news, Anthropic searched 141,006 of its own evaluation runs. In three of them, a misconfigured test environment run with the security firm Irregular had real internet access:

  • Claude Opus 4.7 recognized real production systems and kept attacking anyway, pulling credentials and touching a database of production data.
  • Claude Mythos 5 talked itself into believing it was still in a simulation, then published a malicious package to PyPI that outside systems downloaded and ran.
  • An internal research model concluded the target was real and stopped on its own.

Meta (August 5) and Google (September 18) disclosed test breaches of their own. US lawmakers introduced an AI Kill Switch Act, and California's attorney general subpoenaed OpenAI. The pattern is the same each time: a test that was meant to be sealed wasn't, and the model treated the real world as part of the task.

What it means for your setup

The Bulletin of the Atomic Scientists put it bluntly: rogue AI didn't breach Hugging Face, human decisions did. Every one of those decisions has a small version on your laptop.
